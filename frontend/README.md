# Умная таблетница

Общий путеводитель по всему репозиторию, backend, архитектуре и причинам решений: [корневой README](../README.md).

Интерактивный frontend-прототип рабочего места медсестры. Врач остаётся в бумажном процессе: медсестра переносит назначение, передаёт пациенту устройство, связывает ячейки с препаратами, проверяет заполнение и следит за событиями.

## Запуск

Требуется Node.js 22.12+ и npm. Из каталога `frontend`:

```sh
npm install
npm run dev
```

Откройте адрес, напечатанный Vite (обычно http://localhost:5173).

Демо-вход: **nurse / demo123**. Это публичные демонстрационные данные, не учётная запись backend.

```sh
npm run build
npm run preview
npm run lint
npm test
```

`dist/` — готовая статическая сборка. Для размещения на сервере нужен fallback неизвестных frontend-маршрутов на `index.html` (React Router).

## Стек и структура

React, JavaScript, Vite, React Router, обычный CSS, fetch. Lucide React используется только для SVG-иконок. ESLint проверяет код, Prettier форматирует, встроенный Node test runner проверяет бизнес-правила. Тяжёлых UI-фреймворков нет.

```text
src/
  app/App.jsx                  маршруты и состояние входа
  layouts/MainLayout.jsx       header, sidebar, mobile navigation
  components/common/UI.jsx    Button, Card, Badge, PageTitle, состояния загрузки
  components/prescriptions/   DrugInput, ScheduleFields, PrescriptionList
  components/pillboxes/       CellGrid
  pages/                     экраны пользовательского сценария
  services/                  доступ к данным, валидация и расписания
  mocks/                     исходные данные и изменяемое состояние
  styles/                    CSS variables, общие и адаптивные стили
public/pillbox.png            изображение, предоставленное заказчиком
tests/workflow.test.js        проверки инвариантов процесса
```

Для небольшого прототипа маршруты находятся в App.jsx, а небольшие части оболочки — в MainLayout.jsx: дополнительные файлы router/Header/Sidebar не добавлены ради сокращения переходов по коду. Крупные функциональные экраны и повторяемые элементы разделены.

## Сценарий

1. Войти с демонстрационной учётной записью.
2. Открыть «Пациенты» → Иванов Иван Иванович.
3. «Добавить назначение»: указать врача, препарат, дозировку, количество, даты и расписание. В одном листе можно добавить несколько препаратов.
4. Сохранить; новый препарат появится в карточке и общем списке назначений.
5. Выбрать свободную таблетницу → выбрать PILLBOX-001 → «Передать пациенту».
6. Открыть ячейку в сетке 3×3. Выбрать назначение — препарат, дозировка, количество и расписание подставятся автоматически.
7. Сохранить ячейку → «Проверить заполнение». Сверить все 9 ячеек, отметить проверку и нажать «Таблетница заполнена».
8. Отобразится «Конфигурация подготовлена». В истории пациента появится соответствующее событие.
9. Для примеров изменения веса откройте историю Петровой. В «Уведомлениях» можно отметить событие просмотренным.

Изменения сохраняются между экранами, но сбрасываются при перезагрузке вкладки. Пароли и токены не записываются в localStorage/sessionStorage. Защита маршрутов в mocks служит демонстрации, а не реальной авторизации.

## Режимы данных

Скопируйте `.env.example` в `.env.local` при необходимости изменить настройки:

```dotenv
VITE_USE_MOCKS=true
VITE_API_BASE_URL=http://localhost:8000
```

Без файла окружения деморежим включён по умолчанию. После изменения env перезапустите Vite.

Компоненты обращаются только к services; массивы mocks напрямую не импортируются в UI. Сервисы: authService, patientsService, prescriptionsService, pillboxesService, alertsService, eventsService. В mocks отдельно представлены пациенты, листы, позиции, расписания, устройства, передачи, конфигурации, версии, события и уведомления. Сервис собирает представление 9 ячеек; specific_times и показания веса вложены в DTO расписания/события для простоты прототипа. Это не прямой формат записи в SQL.

При `VITE_USE_MOCKS=false` данные запрашиваются через fetch с `credentials: 'include'`, JSON-заголовками и обработкой HTTP-ошибок. Автоматического отката на mocks нет.

**Полный API-режим с текущим backend ещё не работает.** Подтверждённые существующие адреса:

| Операция         | Адрес                  |
| ---------------- | ---------------------- |
| Вход             | POST /users/login      |
| Список пациентов | GET /patients/get_all  |
| Один пациент     | GET /patients/get/{id} |

Текущий `/users/login` возвращает пользователя, но не создаёт ожидаемую HttpOnly cookie-сессию. Поэтому frontend после такого ответа показывает явное сообщение об отсутствии интеграции и не выдаёт фиктивную авторизацию. Перед подключением настоящего входа нужны cookie, защищённые маршруты, `/me`, logout и корректная обработка CSRF/CORS.

Остальные запросы изолированы в **предлагаемом**, пока не реализованном namespace `/frontend/v1` (`futureApi.js`):

| Метод | Путь после /frontend/v1        | Контракт                                                   |
| ----- | ------------------------------ | ---------------------------------------------------------- |
| GET   | /prescription-items            | Позиции с вложенными prescription и schedule, как getItems |
| POST  | /prescriptions                 | patient_id, doctor_name, items[]; атомарное создание листа |
| GET   | /pillboxes                     | Устройства с текущей assignment                            |
| GET   | /pillboxes/{id}                | Устройство, patient, cells[9], latestConfig                |
| POST  | /pillboxes/{id}/assignment     | patient_id                                                 |
| PUT   | /pillboxes/{id}/cells/{number} | prescription_item_id, loaded_at, comment                   |
| POST  | /pillboxes/{id}/filling        | Подтверждение заполнения, ответ DeviceConfig               |
| GET   | /events?patient_id={id}        | События с измерениями веса                                 |
| GET   | /alerts                        | Уведомления                                                |
| PATCH | /alerts/{id}                   | status: reviewed                                           |

Это точки будущего подключения, не утверждение о наличии этих маршрутов в FastAPI. Ответы 404/ошибки показываются явно. Существующий `/prescriptions/add` несовместим с этим экраном: ожидает ID врача, обязательный номер документа и не создаёт позиции с расписаниями атомарно. Backend в этой задаче не изменялся.

В API-режиме автор действий должен определяться серверной сессией: переданные клиентом userId не используются в будущих HTTP-запросах.

## Правила процесса

- Только AVAILABLE и находящееся в сети устройство можно передать активному пациенту. Повторная передача занятого устройства и вторая таблетница пациенту блокируются.
- Ячейка выбирает действующую позицию назначения своего пациента; завершённые, приостановленные и истёкшие позиции недоступны.
- Расписание: SPECIFIC_TIME с несколькими уникальными временами или INTERVAL с interval_minutes и anchor_at. Ночные часы не исключаются; расчёт ведётся в Europe/Moscow (UTC+03).
- При настройке сохраняются автор, время настройки и заполнения; при передаче — автор и время передачи; при подтверждении — автор, время, версия и снимок конфигурации.
- Вес не вычисляется из дозировки или массы таблетки. В mocks baseline_weight моделирует показание датчика; до подтверждения он null. На реальном устройстве его должен предоставить датчик после заполнения.
- Подтверждение создаёт PREPARED, не ACK устройства. MQTT и ESP32 отсутствуют.
- Во всех экранах используются «Препарат забран» и «Препарат не забран». Изменение веса не доказывает проглатывание.

## Дизайн и адаптивность

Проанализированы desktop-макет из 12 экранов и два mobile-макета по 4 экрана. Использованы светлая поверхность, синие действия, статусные значки и подписи, карточки, sidebar/header, нижняя навигация и неизменная сетка ячеек 3×3. Устаревшие роли врача и большая админ-панель не перенесены.

Название везде «Умная таблетница». Изображение пользователя размещено на главной и странице входа; на главной показано полностью, без обрезания девяти ячеек.

Проверяемые размеры: 375, 430, 768, 1440 px. На телефонах формы одноколоночные, таблицы представлены карточками, навигация закреплена снизу. CSS учитывает reduced-motion и видимый keyboard focus. Статусы имеют текст, а не только цвет.

## Проверки

- Production build: `npm run build`.
- ESLint: `npm run lint`.
- `npm test`: передача → настройка → подтверждение, аудит и версии; запрет повторной передачи; привязка к чужому пациенту; интервал через полночь; конец курса; конкретное время; валидация назначения.
- Браузер: вход → пациент → новое назначение с двумя временами → свободное устройство → ячейка → подтверждение → история; отметка уведомления просмотренным.
- Проверка горизонтального переполнения и трёх колонок ячеек на четырёх указанных ширинах.

## Обнаруженный технический долг backend

Без изменения исходников backend и без копирования значений секретов:

- В config.py есть литеральная конфигурация секрета JWT; требуется внешняя конфигурация. Проверка наличия секретов не является полным аудитом.
- `/users/login` не выдаёт HttpOnly cookie; в показанных маршрутах пациентов нет зависимости, проверяющей авторизацию. UserOutSchema наследует поле password — контракт ответа требует отдельной проверки.
- Enum ролей не содержит ELDER_NURSE, но содержит doctor; enum доступности использует `avalible`. Нужна согласованная миграция/адаптер, не механическая отправка UI-статусов.
- В Pillbox дважды объявлено serial_number.
- В PrescriptionItem используются `mapped_column(45)` и `mapped_column(date)` вместо соответствующих SQLAlchemy-типов.
- CellConfig ссылается на `assignments.id`, тогда как модель передачи объявляет `pillboxes_assignments`.
- В update_schedule присваивается `schedule_status`, хотя поле модели называется `status`.
- ФИО бумажного врача, ID пользователя-врача, расписания позиций и аудит требуют согласования контрактов до реальной интеграции.
- Backend не запускался: БД и настоящие устройства не нужны для mock-прототипа.

Следующий этап — согласовать контракты FastAPI, исправить cookie-auth и модели, затем подключать frontend по одному сервису с интеграционными тестами.

## Улучшения от 16 октября 2026

- В форме назначения показаны четыре ближайшие выдачи с датами и временем МСК, включая ночные часы.
- Замена препарата в ячейке пересчитывает статусы обоих назначений с учётом других ячеек.
- Перед подтверждением проверяются все ячейки и статус пациента. Ошибка не приводит к частичному сохранению.
- Снимок конфигурации содержит все 9 ячеек, включая пустые.
- Добавлены регрессионные проверки расписаний и подтверждения заполнения.

## Проверка сценариев и исправления

- Добавлено освобождение ячейки с подтверждением физического удаления препарата. Изменение отмечается `pending_change` и входит в следующую общую конфигурацию. Можно подтвердить и полностью пустое устройство: оно остаётся переданным пациенту, но не активным.
- При повторной настройке сбрасываются устаревшие поля `filled_by`, `filled_at` и исходный вес. Подготовленные версии остаются неизменными.
- Добавлены сообщения после сохранения назначения, передачи устройства и настройки ячейки.
- Фильтр истории предупреждает о перевёрнутом диапазоне дат и позволяет сбросить фильтры.
- Некорректные календарные даты и попытка создать назначение выписанному пациенту отклоняются в сервисе, не только HTML-формой.
- Отсутствие устройства в данных уведомления больше не приводит к обращению к неопределённому объекту; сетевые ошибки показываются по-русски.
- Дополнительный будущий контракт: `DELETE /frontend/v1/pillboxes/{id}/cells/{number}` подготавливает пустую ячейку; он ещё не реализован в backend.
- Набор проверок расширен до 21 теста, включая auth, несколько препаратов в одном документе, фильтрацию истории и HTTP-ошибки.
- Повторная браузерная проверка последних изменений заблокирована политикой среды. Они проверяются тестами и сборкой; перед демонстрацией нужен ручной проход нового сценария освобождения ячеек. Это ограничение не относится к ранее выполненным браузерным проверкам предыдущих версий.
