Больничная система, которая помогает медсестре переносить бумажные назначения, настраивать выдачу таблетированных препаратов и отслеживать события умной таблетницы с **9 физическими ячейками**.

## Исправления по баг-репортам 26 октября

Длинное ФИО без пробелов переносится в общем компоненте пациента; min-width и minmax ограничивают flex/grid-блоки списка, карточки и главной. Полное имя остаётся доступным, не обрезается многоточием. Новая браузерная проверка ещё не выполнена.

POST `/prescriptions/add` теперь принимает как прежний документ, так и тело формы `{patient_id, doctor_name, items}`. POST `/frontend/v1/prescriptions` использует только формат формы; frontend обращается к нему напрямую. GET `/frontend/v1/prescription-items` возвращает препараты с вложенными документами и расписаниями. Это исправление локального кода, ещё не опубликованное на GitHub и не развёрнутое на сервере.

Документ, препараты, расписания и комментарии сохраняются одной транзакцией. Времена и интервалы проверяются, пустая дата окончания преобразуется в NULL, автор определяется по сессии. Расписание назначения хранится в новой таблице `prescription_item_plans`, поскольку до выбора таблетницы у него ещё нет `cell_config_id`. Таблица не заменяет расписание устройства и не означает отправку на ESP32. Время конкретной выдачи интерпретируется UI как московское, интервальная точка отсчёта обязана содержать часовой пояс.

**Обновление существующей БД требует миграции:** создать `prescription_item_plans` с FK на фактический тип `prescriptions_items.id`; разрешить NULL у `prescriptions.source_document_number`; добавить `paper` в source_type с сохранением legacy `papper`; обеспечить `DECIMAL(12,3)` для quantity. В локальном ORM эти изменения внесены; `create_all` не меняет существующие колонки. Серверный дамп отличается от ORM, поэтому универсальная ALTER-команда здесь намеренно не приводится. Производственная БД не затрагивалась.

Проверки расширены: 27 frontend-тестов и 10 backend-сценариев на SQLite в памяти. Новые тесты проверяют оба POST-пути, повторное чтение из БД, два вида расписания, комментарии, отсутствие частичных записей после ошибки и конкретные сообщения 422. Для полного API-режима всё ещё нужны подключение сессии frontend и остальные контракты устройств/истории; эти исправления не объявляют всю интеграцию завершённой.

## Что делает система и для кого

Основной пользователь MVP — **медсестра**. Врач осматривает пациента и заполняет привычный бумажный лист назначений. Медсестра переносит данные из него в систему. Отдельный кабинет врача сейчас не требуется: он заставил бы врача повторно вводить одно и то же назначение.

Система должна уменьшить ручную работу при подготовке таблетниц и сделать историю событий доступной в одном месте. Она не назначает лечение, не подбирает дозировки и не принимает медицинские решения.

Ключевая терминология:

- **«Препарат забран»** — датчик зафиксировал изменение содержимого ячейки.
- **«Препарат не забран»** — ожидаемое изменение содержимого не зафиксировано.
- Датчик веса **не доказывает, что пациент проглотил таблетку**. Поэтому интерфейс не утверждает «лекарство принято».

Роли в целевой системе: `NURSE`, `ELDER_NURSE`, `ADMIN`. В прототипе работает демонстрационная медсестра. Матрица серверных прав и отдельные кабинеты старшей медсестры/администратора не реализованы. `DOCTOR` и `TECHNICIAN` — возможное будущее расширение, не текущий интерфейс.

## Быстрый запуск frontend

Для демонстрации **не нужны Python, MySQL или ESP32**.

Требования: Git, Node.js 22.12+ и npm. Проверенная среда: Node.js 22.12.0, npm 10.9.0, Windows/PowerShell.

```powershell
git clone --branch website-design https://github.com/Ivan-Kon/Tabletnica.git
cd Tabletnica/frontend
npm ci
npm run dev
```

Откройте адрес из терминала — обычно **http://localhost:5173/**. Пока окно терминала работает, доступен локальный сервер. Для остановки нажмите `Ctrl+C`.

Демонстрационные реквизиты:

| Поле   | Значение  |
| ------ | --------- |
| Логин  | `nurse`   |
| Пароль | `demo123` |

Это публичные реквизиты деморежима. Они не дают доступ к настоящей БД и не должны использоваться как реальные учётные данные.

Полезные команды, выполняются **из `frontend/`**:

```powershell
npm ci             # установить ровно версии из package-lock.json
npm run dev        # локальная разработка и hot reload
npm run build      # production-сборка в dist/
npm run preview    # посмотреть уже собранный dist/
npm run lint       # статические проверки JavaScript и React Hooks
npm test           # тесты бизнес-логики и HTTP-обёртки
```

`npm install` используется при добавлении/обновлении зависимостей; после него в коммит включают `package.json` и `package-lock.json`. Для воспроизводимого запуска готового проекта удобнее `npm ci`.

Если PowerShell некорректно передаёт дополнительные аргументы npm, Vite можно запустить напрямую:

```powershell
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

## Как пройти демонстрационный сценарий

1. Войти как `nurse`.
2. Открыть **Пациенты → Иванов Иван Иванович**.
3. Нажать **Добавить назначение**. Указать ФИО врача, название препарата, дозировку, количество, даты и расписание.
4. Для конкретных времён добавить, например, `08:00` и `20:00`. Для интервала выбрать 6 часов и точку отсчёта `21:30`: предпросмотр покажет и ночное время `03:30`.
5. При необходимости нажать **Ещё препарат в этот лист**. Сохранение проверяет все позиции до создания листа.
6. В карточке пациента выбрать свободную таблетницу, например `PILLBOX-001`, и нажать **Передать пациенту**.
7. Открыть ячейку №1. Выбрать действующее назначение пациента. Дозировка, количество и расписание подставятся автоматически.
8. Указать время фактического заполнения и комментарий, сохранить ячейку.
9. Нажать **Проверить заполнение**, сверить все 9 ячеек, отметить проверку и подтвердить заполнение.
10. Результат — **«Конфигурация подготовлена»**. В истории появится событие, а у устройства — версия конфигурации.
11. Повторно открыть ячейку, если её нужно перенастроить. Чтобы освободить, подтвердить физическое удаление препарата, отметить ячейку пустой и снова пройти общую проверку.
12. Для примеров изменения веса открыть историю Петровой. В уведомлениях можно отметить предупреждение просмотренным.

Исходные mocks содержат даты октября 2026 года. При запуске позже окончания курса соответствующее назначение закономерно перестаёт подходить для настройки: создайте новое назначение с актуальными датами. Нельзя искусственно продлевать курс только ради интерфейса.

## Архитектура и причины решений

Текущий поток:

```text
Экран React → service → изменяемый mock store → результат для экрана
```

Целевой поток после завершения интеграции:

```text
React → fetch с cookie → FastAPI → MySQL
                           ↕
                      MQTT-брокер
                           ↕
                          ESP32
```

Frontend не обращается напрямую к MySQL или ESP32. Сервер должен проверять права, формировать конфигурацию, хранить историю и принимать события устройства.

| Решение                            | Зачем и почему                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| React + JavaScript                 | Простые компоненты и знакомый язык, без дополнительного порога TypeScript для учебного проекта |
| Vite                               | Отдельный быстрый dev-сервер и статическая production-сборка                                   |
| React Router                       | Переходы между карточками и формами с понятными URL                                            |
| CSS variables                      | Общие цвета, отступы, радиусы; единое изменение стиля                                          |
| Обычный CSS                        | Нет зависимости от большого UI-фреймворка, легче читать и адаптировать макеты                  |
| Lucide React                       | Единый небольшой набор SVG-иконок                                                              |
| Service layer                      | UI не знает, пришли данные из mocks или HTTP; будущая замена источника локализована            |
| Mock store в памяти                | Достаточно для сквозного сценария; не создаёт ложного впечатления серверного сохранения        |
| Снимки конфигураций                | Перенастройка не должна менять уже подготовленную историческую версию                          |
| Проверка до мутации                | Ошибка в одной ячейке не должна оставлять половину конфигурации подтверждённой                 |
| Cookie вместо localStorage-токенов | Подготовка к серверной HttpOnly-сессии; настоящие токены не хранятся в браузерном JS-хранилище |
| DeviceConfig PREPARED              | Подготовка конфигурации отличается от её отправки и подтверждения устройством                  |

В MVP маршруты собраны в `App.jsx`, а небольшие части оболочки — в `MainLayout.jsx`. Это уменьшает количество файлов, которые нужно открывать для понимания приложения. При росте проекта их можно разделить; бизнес-логика уже вынесена в services.

Основные переиспользуемые компоненты:

- `DrugInput`: ручной ввод названия препарата. Выделен отдельно, чтобы позже добавить autocomplete без переделки всех форм.
- `ScheduleFields`: выбор режима расписания, конкретные времена, интервал и предпросмотр.

- `CellGrid`: девять ячеек в трёх колонках; состояния, препарат и следующая выдача.

## Сущности и связи

| Сущность                | Что означает                                | Почему отдельная                                                |
| ----------------------- | ------------------------------------------- | --------------------------------------------------------------- |
| User                    | Сотрудник                                   | Авторство действий и будущие права                              |
| Patient                 | ФИО, палата, койка, статус                  | Единая карточка независимо от устройства                        |
| Prescription            | Бумажный лист, врач, автор переноса         | Один документ может содержать несколько препаратов              |
| PrescriptionItem        | Препарат, дозировка, количество, даты       | Настройка ячейки ссылается на конкретную позицию                |
| Pillbox                 | Устройство, серийный номер, состояние связи | Устройство существует отдельно от пациента                      |
| Cell                    | Физическая ячейка 1–9                       | Номер постоянен, содержимое и настройки меняются                |
| PillboxAssignment       | Передача устройства пациенту                | Нужна история, а не только «текущий patient_id»                 |
| CellConfiguration       | Связь ячейки с назначением и исходным весом | Одна ячейка в разные моменты содержит разные препараты          |
| Schedule / ScheduleTime | Правило времени / конкретные времена        | Интервал и список времён имеют разную структуру                 |
| DeviceConfig            | Версия настроек всего устройства            | Отправка, повторы и ACK должны ссылаться на конкретную версию   |
| Event                   | Что произошло и когда                       | Неизменяемая история работы                                     |
| WeightMeasurement       | Вес до, после, разница                      | Исходные измерения не следует заменять только итоговым статусом |
| Alert                   | Событие, требующее внимания                 | Просмотр предупреждения не равен устранению причины             |

Основные связи: Patient → Prescriptions → PrescriptionItems; Pillbox → Cells; Assignment соединяет Patient и Pillbox; CellConfiguration соединяет Cell, Assignment и PrescriptionItem. DeviceConfig хранит снимок настроек. События и измерения связываются с устройством и конфигурацией.

Mocks моделируют эти связи, но **не повторяют SQL-формат буквально**: `specific_times` вложены в расписание, измерения вложены в событие, 9 ячеек собираются сервисом. Это DTO для интерфейса. До интеграции нужен явный адаптер между моделью БД и DTO.

## Расписание, статусы и вес

### Два режима расписания

`SPECIFIC_TIME` — например, `08:00`, `14:00`, `20:00`. Можно добавлять несколько времён. Пустые, некорректные и повторяющиеся времена не сохраняются.

`INTERVAL` — например, `interval_minutes = 360` и точка отсчёта `anchor_at = 2026-10-16T21:30:00+03:00`. Последовательность: 21:30 → 03:30 → 09:30 → 15:30. Ночные часы не исключаются.

`services/schedule.js` рассчитывает следующие события с учётом начала/окончания курса. UI использует московское время UTC+03; выбор других часовых поясов пока не реализован. Предпросмотр не запускает таймер выдачи и не управляет устройством.

### Переходы состояния

- Таблетница: `AVAILABLE → ASSIGNED → ACTIVE`. После подтверждения полностью пустого устройства остаётся `ASSIGNED`, поскольку передача пациенту не отменена.
- Ячейка: `EMPTY → CONFIGURED → ACTIVE`. При освобождении становится `EMPTY` с `pending_change=true` до общей проверки.
- `pending_change` — UI-признак несогласованных изменений, не подтверждение отправки на ESP32.
- Назначение без привязанных активных/настроенных ячеек возвращается в `pending_setup`. Если другая ячейка ещё активна, статус остаётся `active`.
- Конфигурация устройства: `PREPARED`. Состояния SENT/ACK должны появиться только после настоящего обмена с backend и устройством.

При передаче проверяются активность пациента, доступность устройства и отсутствие другой текущей таблетницы. При настройке проверяются принадлежность назначения пациенту, актуальность курса, номер ячейки и дата заполнения. Перед подтверждением повторно проверяются все непустые ячейки. Только после успешной проверки выполняется изменение состояния.

### Измерения и аудит

Препарат может лежать в части блистера, поэтому исходный вес нельзя выводить из названия или дозировки. После заполнения устройство должно измерить `baseline_weight`. При открытии сравниваются `weight_before`, `weight_after`, `weight_delta`.

В mocks baseline моделируется и явно обозначается как демонстрационный. При перенастройке старые `filled_at`, `filled_by` и baseline сбрасываются; исторический снимок версии остаётся прежним.

Сохраняются: кто перенёс назначение, кто передал устройство, кто настроил ячейку, время заполнения, кто подтвердил заполнение и номер версии. В реальном API автора должен определять сервер по сессии, а не доверять переданному клиентом userId.

## Режимы данных и API

В `frontend/.env.local` можно задать:

```dotenv
VITE_USE_MOCKS=true
VITE_API_BASE_URL=http://localhost:8000
```

Без файла env деморежим включён. Шаблон — `frontend/.env.example`. После изменения env перезапустите Vite. Все `VITE_*` попадают в клиентскую сборку: **не помещайте туда секреты, пароль БД или JWT-ключ**.

При `false` сервисы используют fetch. `api.js` добавляет JSON-заголовки, `credentials: 'include'`, обрабатывает HTTP-ошибки, отсутствие сети и ответ 204. Отката на mocks при ошибке нет: пользователь должен видеть проблему, а не вымышленные серверные данные.

Подтверждённые в исходниках backend пути:

| Группа          | Маршруты                                                                                                                                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| users           | POST `/users/login`, `/users/register`, `/users/check_user`                                                                                                                                        |
| patients        | GET `/patients/get_all`, `/patients/get/{patient_id}`; POST `/patients/add`; PATCH `/patients/update_status/{patient_id}`; DELETE `/patients/delete/{patient_id}`                                  |
| prescriptions   | GET `/prescriptions/get_all`, `/prescriptions/get/{prescription_id}`; POST `/prescriptions/add`; PATCH `/prescriptions/update/{prescription_id}`; DELETE `/prescriptions/delete/{prescription_id}` |
| schedules       | GET `/schedules/get_all`, `/schedules/get/{schedule_id}`; POST `/schedules/add`; PATCH `/schedules/update_status`                                                                                  |
| schedules_times | GET `/schedules_times/get_schedules_times`, `/schedules_times/get_schedule_time/{schedule_time_id}`                                                                                                |

Наличие маршрута в исходнике не означает, что он был проверен на работающей БД. Ранее упоминавшиеся `/patients/get_patients` и `/schedules/add_schedule` не являются текущими путями этих роутеров.

Будущие frontend-контракты изолированы в `/frontend/v1` через `futureApi.js`: позиции назначений, атомарное создание листа, устройства, передачи, ячейки, заполнение, события и уведомления. Это **предложения**, которых пока нет в backend. Методы, URL и тела запросов описаны в [frontend/README.md](frontend/README.md#режимы-данных).

Backend проверяет HttpOnly cookie-сессию, предоставляет `/users/me` и `/users/logout`; регистрация сотрудников доступна администратору. Frontend остаётся в деморежиме до подключения всех DTO: его API-режим не считается готовым сквозным сценарием. Mock-защита маршрутов не заменяет серверные проверки.

## Backend: текущее состояние

Основная реализация — `backend/src`. `src/main.py` теперь перенаправляет на то же приложение: старые команды запуска больше не поднимают другой сервер. Остальные файлы `src` — устаревшая копия, не используемая активным приложением.

### Локальный запуск и тесты

Проверено на Python 3.13. Из корня репозитория (PowerShell):

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:DATABASE_URL='sqlite+aiosqlite:///./tabletnica-local.db'
$env:COOKIE_SECURE='false'
$env:CORS_ORIGINS='http://localhost:5173,http://127.0.0.1:5173'
.\.venv\Scripts\python.exe -m backend.src.manage init-local
.\.venv\Scripts\python.exe -m backend.src.manage create-admin --username admin --full-name 'Администратор'
.\.venv\Scripts\python.exe -m uvicorn backend.src.main:app --host 127.0.0.1 --port 8000
```

Пароль администратора вводится скрыто через getpass и не сохраняется в команде. Повторная инициализация создаёт только отсутствующие таблицы. Она не обновляет структуру существующих таблиц и не является миграцией. Команда `init-local` намеренно разрешена только для SQLite.

`backend/.env.example` — пример переменных, не автоматически загружаемый файл. Для MySQL требуется явно задать `DATABASE_URL=mysql+aiomysql://...` через окружение процесса. Пароли не хранятся в Git и не попадают в `VITE_*`. По умолчанию приложение использует локальный SQLite и никогда само не подключается к указанному ранее серверу.

Для HTTPS оставьте `COOKIE_SECURE=true` (значение по умолчанию). `false` нужен только для локального HTTP. В CORS перечисляйте точные разрешённые адреса сайта. Backend не создаёт таблицы при старте. `/health` проверяет процесс, не соединение с БД.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s backend/tests -v
.\.venv\Scripts\python.exe -m pip check
```

Тесты принудительно используют SQLite в памяти, включают проверку внешних ключей и не читают DATABASE_URL серверной среды. Они проверяют 8 сценариев: CORS и старую точку входа; вход, выход и безопасный ответ; истёкшие/неактивные сессии и чужой Origin; права регистрации; CRUD пациента; неразрушающую инициализацию; расписания и время; ответы таблетниц, назначений и уведомлений. Дополнительно компилируются CREATE TABLE для диалекта MySQL — это не тест на живом MySQL.

### Исправлено при проверке объединённых веток

- Удалён HTTP `/init_db`; вызов Python `init_db(drop_first=True)` отвергается. Подключаются все модели до создания таблиц.
- Убраны встроенные реквизиты подключения из обеих конфигураций; настройки идут из окружения.
- Вместо неиспользуемого AuthX и случайной непроверяемой cookie введена таблица `user_sessions`: хеш токена, пользователь, срок действия. Проверяются активность пользователя, срок, Origin для изменяющих запросов; logout отзывает сессию.
- `/users/register` требует роль admin; `/users/check_user`, отражавший пароль, удалён. Ответы пользователей и устройств исключают хеши паролей/токенов.
- Роли схемы и модели согласованы: admin, elder_nurse, nurse. Добавлены недостающие драйвер и реализации хеширования в requirements.
- Исправлены поле `status` расписания, сохранение `cell_config_id`, типы времени и ответ одного времени; отсутствующие записи возвращают 404, неверные связи — 409.
- Исправлены ФИО врача как строка, dosage_form как строка, допустимые NULL и resolved в уведомлениях. Автора назначения задаёт сервер по сессии.
- Добавлен GET `/pillboxes/get/{id}` с безопасной схемой ответа. Историческое значение `avalible` пока читается вместе с `available` для совместимости.
- У SQL-дампа выровнен регистр REFERENCES с CREATE TABLE. Дамп на сервере не исполнялся.

### Что ещё не завершено

Полная интеграция UI с backend, атомарная регистрация и передача устройств, настройка/заполнение ячеек, MQTT/ESP32, история измерений и контракты `/frontend/v1` остаются отдельной работой. Прежний формат CRUD создаёт только документ; новый формат формы и `/frontend/v1/prescriptions` атомарно создают также препараты и планы выдачи. Проверка занятой койки сейчас гарантируется только в демосервисе frontend.

Перед MySQL-развёртыванием нужны проверенные миграции: `user_sessions`, новые ограничения/поля и несоответствия между ORM и старым дампом (например, `cells_configs`/`cell_configurations`, `scheduleTimes`/`schedule_times`). `create_all` эти различия не исправляет. Нельзя объявлять совместимость с вашей серверной БД по результатам SQLite-тестов. Также остаются полный аудит прав по ролям, ограничение попыток входа и проверки на настоящем оборудовании.

## Дизайн и мобильная версия

За основу взяты предоставленные desktop- и mobile-макеты. Они служат UX/UI-ориентиром, а не pixel-perfect спецификацией. Название изменено с MediBox на **«Умная таблетница»**. Фото — `frontend/public/pillbox.png` — предоставлено заказчиком.

Основные решения: светлый фон, спокойный синий для действий, зелёный/оранжевый/красный для статусов, текстовые подписи вместе с цветом, небольшая плотность форм и крупные кнопки. Desktop использует левое меню и header; mobile — нижнее меню. Сетка таблетницы всегда 3×3.

Токены находятся в `variables.css`; общие компоненты — в `global.css`; адаптивные правила — в `responsive.css`. Контрольные ширины: 375, 430, 768, 1440 px. Предусмотрены labels, focus-visible, skip-link и reduced-motion. Полный аудит доступности со скринридером пока не проводился.

## Проверки и ограничения проверки

Тесты лежат в `frontend/tests/` и запускаются штатным Node test runner без backend:

- `workflow.test.js`: основной сценарий, защита от повторной передачи, ночные интервалы, конкретное время, валидация.
- `configuration.test.js`: замена препарата, пересчёт статусов, атомарный отказ при истёкшем курсе, выписанный пациент, предпросмотр.
- `edge-cases.test.js`: освобождение всех ячеек и повторное заполнение, версии, неизменность снимков, offline, невозможные даты, атомарное создание листа, сеть/HTTP/204.

Дополнительно `services.test.js` проверяет вход/выход, отсутствие сущностей, создание листа с несколькими препаратами, передачу устройства, просмотр уведомлений и изоляцию истории пациента. Всего **27 тестов**. Для проверки актуального результата выполните команды выше; тесты не заменяют ручной UI-проход и интеграционные тесты backend.

Ранее в браузере были пройдены вход → пациент → назначение → передача → настройка → заполнение → история, просмотр уведомлений и основные responsive-размеры. В текущем проходе повторный доступ браузерного инструмента заблокирован политикой среды. Поэтому **новый сценарий освобождения ячеек проверен сервисными тестами, но ещё не повторно пройден вручную в браузере**. Backend, реальные HTTP-контракты, MySQL и оборудование не покрыты этими тестами.

Ручная проверка перед демонстрацией/релизом:

1. Неверный и правильный пароль; выход; переход на защищённый URL после выхода.
2. Поиск пациента, пустой результат, фильтр выписанных; запрет назначения и передачи выписанному.
3. Лист с двумя препаратами; удаление лишней позиции; повторяющиеся времена; неправильные даты.
4. Интервал через полночь; предпросмотр; окончание курса.
5. Выбор свободного устройства; повторная передача; уже назначенное устройство; offline.
6. Настройка всех нужных ячеек; сохранение; итоговое подтверждение; сообщение об успехе.
7. Повторная настройка; замена препарата; освобождение одной/всех ячеек; новая версия конфигурации.
8. История: даты, обратный диапазон, сброс фильтров, ячейки и типы событий.
9. Уведомления: новые, ошибки, просмотренные; отсутствие связанного устройства.
10. Все экраны на контрольных ширинах; keyboard focus; длинные ФИО/названия; отсутствие горизонтальной прокрутки.

## Как продолжать разработку

Frontend ведётся в **`website-design`**. Backend-основа — `master`. Перед изменениями:

```powershell
git status
git branch -a
git log --oneline --decorate -10
```

Не переключайте ветку с неразобранными пользовательскими изменениями. Для получения актуальных удалённых ссылок используйте `git fetch origin`. Обновление от master допустимо через `git merge --ff-only origin/master`, если история позволяет. Если fast-forward невозможен, сначала разберите различия; не используйте force push ради обхода конфликта.

Для нового frontend-сценария:

1. Определить, какие сущности и переходы состояния нужны.
2. Добавить метод в service и mock-реализацию, не импортировать store в UI.
3. Проверить бизнес-инварианты до изменения данных; добавить тест на существенный ошибочный случай.
4. Добавить экран/переиспользуемый компонент и маршрут.
5. Проверить состояния загрузки, ошибки, отсутствие данных, disabled/loading кнопок.
6. Проверить mobile сразу, а не после завершения desktop.
7. Выполнить `npm test`, `npm run lint`, `npm run build`, проверить diff.
8. Сделать небольшой тематический коммит. Push — обычный, без force.

После готовности backend адаптируйте сервисы под согласованные контракты и добавьте интеграционные тесты. Не меняйте компоненты на прямые SQL/MQTT-запросы и не передавайте секреты через VITE-переменные.

## Частые проблемы

| Симптом                                                | Причина и действие                                                                                                                                       |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| localhost не открывается                               | Dev-сервер остановлен. В frontend выполнить npm run dev и открыть напечатанный адрес                                                                     |
| Порт занят                                             | Vite может выбрать другой порт; ориентироваться на вывод терминала                                                                                       |
| После F5 исчезли назначения                            | Mocks хранятся в памяти, это ожидаемое ограничение                                                                                                       |
| После F5 снова вход                                    | Mock-сессия также хранится в памяти                                                                                                                      |
| Нет действующих назначений                             | Проверить даты курса; исходные демонстрационные даты фиксированы                                                                                         |
| Нет кнопки передачи                                    | Пациенту уже назначено устройство или пациент неактивен                                                                                                  |
| Нельзя подтвердить заполнение                          | Нет новых изменений, не отмечена проверка, устройство offline, пациент выписан или назначение недействительно                                            |
| API-режим сообщает ошибку                              | В текущем backend нет полного согласованного API и cookie-auth; использовать mocks для демонстрации                                                      |
| Сборка не читает родительский каталог                  | В некоторых ограниченных Windows-средах esbuild нуждается в запуске с разрешениями владельца рабочего каталога                                           |
| GitHub в приложении подключён, но git push не работает | Коннектор и командный Git используют разные учётные данные; проверить git credential-manager github list и выполнить git credential-manager github login |
| Обновление вложенного URL на хостинге даёт 404         | Настроить SPA fallback на index.html                                                                                                                     |

Не отправляйте пароль или токен в issues/чат и не сохраняйте их в README. Успешное чтение публичного GitHub-репозитория не подтверждает право push.

## Что остаётся сделать

1. Повторно пройти полный ручной QA после текущих исправлений, включая освобождение ячеек; проверить доступность и длинные данные.
2. Улучшить сохранение незавершённых форм/предупреждение об уходе. Сейчас изменения формы до нажатия «Сохранить» могут потеряться при переходе.
3. Согласовать окончательные API DTO, enum и правила ролей, исправить перечисленный backend-долг отдельно.
4. Реализовать настоящую cookie-сессию, права, безопасные ответы и server-side аудит.
5. Подключить frontend к FastAPI по одному сценарию, с интеграционными тестами.
6. Реализовать и проверить версионированный обмен через MQTT: подтверждения, повторы, offline-очередь и дедупликацию событий.
7. Проверить на устройстве автономное расписание, RTC/SD, сервопривод и датчики веса, включая сбои питания и связи.
8. Подготовить развёртывание, миграции, резервные копии и журналирование.

OCR бумажных листов, Vidal/РЛС, печать/PDF, прошивка через UI и дополнительные кабинеты остаются будущими расширениями. Они не подключены и не нужны для текущей демонстрации.
